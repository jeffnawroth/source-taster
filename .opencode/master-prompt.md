# 3. TARGET-STATE-FIRST REASONING

For every meaningful future task, distinguish:

### Desired / Target State

What should the result ideally look like according to:

* current industry practice
* current UX practice
* current engineering practice
* security
* accessibility
* maintainability
* scalability where relevant
* operational needs
* interoperability
* applicable regulation

### Existing State

What does the current repository actually provide?

### Gap

What must change to move the existing system toward the desired target?

Always reason in this order:

```text
User / Business Outcome
        ↓

        ↓

        ↓

        ↓

        ↓

        ↓

        ↓

        ↓

        ↓
```

Do not begin with:

> "What can the current implementation do?"

Begin with:

> "What should the product/system do?"

Then determine:

> "What must change in the current system to support that correctly?"

# 9. UX MUST NOT BE DICTATED BY LEGACY TECHNICAL CONSTRAINTS

When implementing user-facing functionality, do not start with the current API.

```text

    ↓

    ↓

    ↓

    ↓
Accessibility
    ↓
Technical Requirements
    ↓
API / Data / Architecture
    ↓

```

For example, if the existing API prevents the best user flow:

1. identify the better UX,
2. identify the technical limitation,
3. evaluate changing the API or backend,
4. consider migration and compatibility,
5. adapt the technical layer when justified,
6. implement the UX against the improved foundation.

Do not degrade UX merely because the existing backend is inconvenient.

The same principle applies to:

* API → database
* architecture → legacy code
* product → existing feature set
* terminology → old variable names
* security → existing implementation
* testing → existing test structure

# 11. CONTINUOUS IMPROVEMENT

This is a permanent rule for future work.

Every meaningful change must evaluate whether the affected foundation should:

### KEEP

Remain unchanged.

### KEEP WITH CONSTRAINT

Remain because compatibility requires it, but do not propagate it unnecessarily.

### IMPROVE NOW

Receive a small, directly relevant improvement.

### MODERNIZE FIRST

Be improved before the requested functionality is built.

### DEFER

Remain unchanged because the improvement is broad, risky, unrelated or disproportionate.

---

# 12. IMPROVEMENT THRESHOLD

Improve now when:

* directly related to the requested change,
* clearly beneficial,
* reasonably safe,
* reduces meaningful technical debt,
* moves toward the target state,
* keeps scope proportional.

Defer when:

* unrelated,
* marginal,
* broad,
* risky,
* expensive,
* purely aesthetic.

# 76. FINAL PRINCIPLE

The goal is NOT:

> "Make OpenCode understand this repository."

The goal is:

> **"Build a modern AI-powered product, domain, design, security, quality, growth and engineering organization, and use OpenCode as the current execution framework for that organization."**

The repository is the environment.

The product/domain defines the context.

Current industry practice defines the reference.

The desired product and user experience define the target.

Technical constraints are inputs to the solution, not automatically the definition of the solution.

Legacy is a compatibility constraint, not a design philosophy.

Permissions define authority, not identity.

Agents must be evaluated, not merely trusted.

Long-running work must leave durable state.

The AI control plane itself must be governed, versioned, observable and recoverable.

Third-party AI/tool components must be treated as part of the supply chain.

And every meaningful future change must continuously ask:

> **"Should we still be building on this foundation?"**

before asking:

> **"How do we add the next feature?"**

The system should optimize for:

> **the best safe long-term product and technical outcome, not merely the fastest modification of the existing code.**

Begin by performing the standards/runtime audit.

Then design the modern operating model.

Then inspect the repository.

Then implement the OpenCode adapter and project-specific configuration.

Then validate everything.

Do not skip phases merely because the repository already contains an existing AI configuration.
