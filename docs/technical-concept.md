# Source Taster technical concept and qualification handoff

This is the consolidated planning view for [Final technical-concept synthesis and requirements traceability](https://github.com/jeffnawroth/source-taster/issues/60), under the [decision map](https://github.com/jeffnawroth/source-taster/issues/4). The baseline is the client-approved [requirements specification v3.4](requirements-specification.md) as of commit [`5a0a786`](https://github.com/jeffnawroth/source-taster/blob/5a0a78676803260c5722f6812b56663115c7a4ad/docs/requirements-specification.md). Version 3.4 changes only the FA-ERF-03 acceptance criterion against v3.3 ([`bf6b3fd`](https://github.com/jeffnawroth/source-taster/blob/bf6b3fd229602e867223497d6378258fead6f338/docs/requirements-specification.md)), which the first coverage audit used. The reviewed design snapshot comprises [GLOSSARY.md](../GLOSSARY.md) and ADRs 0001–0026 at [`5a0a786`](https://github.com/jeffnawroth/source-taster/tree/5a0a78676803260c5722f6812b56663115c7a4ad/docs/adr).

The [traceability matrix](requirements-traceability.md) accounts for all **200 numbered requirements: 118 must, 17 should and 65 deferred**, plus unnumbered launch constraints and preparation. A mapped mechanism is a design record, **not an implemented feature or passed acceptance test**. Evidence gates below remain open until execution supplies their results. This synthesis does not change obligations, select an unapproved fallback, execute reviews, provision services, collect a corpus or create an implementation backlog.

**Coverage review result: no launch design decision remains open.** The first audit found four gaps; each is now resolved by an accepted ADR, and the re-audit of the matrix against v3.4 and ADRs 0001–0026 found no further one. Every must requirement and every §12.1/§19 preparation row has a selected mechanism or preserved seam. What remains is implementation, the open qualification packets Q01–Q11 and the unadopted change-request candidates C01–C06. Unselected items in the matrix are provisioning or qualification, not design: the actual domain and EU support mailbox provider are bought within ADR-0020's `support@<domain>` design, and BYOK key persistence belongs to a deferred feature. A failed qualification reopens a precise decision; it is not a hidden open choice today.

## Product and program boundaries

Source Taster checks existence and bibliographic agreement, with an explanation and eligible Correction suggestion. Human judgment remains final. Plagiarism, style-conformity judgment, statement-support checking at launch, unsupported Source types and launch organization/API offerings remain outside the product boundary in specification section 17.

The shared web/extension verification UI calls the **open verification API** for every verification function. That program owns Structuring, search, scoring, Checks, results, History and Verification reports. The **private service** owns Accounts, current authorization, hosted entitlement/Quota, Orders, billing, DPA records and routine Operator administration. Clients call its account/session/Plan APIs directly; it never proxies verification payloads. Programs communicate through narrow, contract-first internal APIs using opaque identifiers/counts/permissions. There are no cross-schema reads or foreign keys.

| Responsibility | Selected boundary | Authoritative record |
| --- | --- | --- |
| Open product | AGPL-3.0-or-later core, verification clients and shared domain implementation; standalone developer checks are explicit configuration, not hosted entitlement bypass | [ADR-0001](adr/0001-open-core-boundary.md), [ADR-0003](adr/0003-system-architecture.md) |
| Proprietary service/UI | Account, commerce and Operator implementations; private status/audit data contains no verification content | ADR-0001, [ADR-0014](adr/0014-operator-administration.md) |
| Public transport contracts | Project-owned schemas, transport types and associated clients under AGPL-3.0-or-later OR MIT; no imported AGPL implementation through type inference | [ADR-0002](adr/0002-tech-stack.md) |
| Persistence/jobs | One EU PostgreSQL instance initially, separate schemas/roles/queues; pg-boss jobs and ordered SSE events; trusted workers own persistence and external dispatch | ADR-0003, [ADR-0012](adr/0012-hosting-operations.md) |
| Untrusted extraction | OS-enforced restricted execution area; bounded input/output and no database credentials, service keys or unrestricted network | [ADR-0015](adr/0015-security-abuse-protection.md) |
| Content delivery | Verification program delivers directly to the currently entitled recipient; private Operator administration coordinates status, never previews or relays full verification exports | ADR-0014, [ADR-0021](adr/0021-online-dpa-workflow.md) |

Repository/process/API separation is an engineering design, not legal proof that works are independent. Source-offer, CLA, third-party code/assets/fonts/styles, generated clients and actual communication remain subject to Q10 and Q05.

## Selected implementation route

Use TypeScript end to end: the ADR-0002 Node/TypeScript release lines, React/Vite/TanStack SPA, Hono and Zod/OpenAPI contracts, PostgreSQL/Prisma/pg-boss, fetch-based SSE, React Aria/Tailwind and per-program Paraglide catalogs. Exact release lines, compatibility fallbacks and production dependency inventories belong to ADR-0002; the dated selections are not a cleared lockfile or proof of present vendor support.

The extension is an explicit Vite target with bundled local code/assets and an owned adapter for Chromium `sidePanel` and Firefox `sidebarAction`. No remote executable code or second extension framework is selected. Selection intake takes only the browser's native `selectionText` from a `selection` context-menu entry and opens the panel before any `await`; it needs no `scripting` or host permission unless Q01 triggers ADR-0026's Chromium line-break contingency. Both clients share verification presentation and server defaults. Interface language and preferred citation style are Preferences: Account-authoritative when signed in, local per client environment for Guests ([ADR-0023](adr/0023-user-preferences.md)). Sign-in sessions are separate, but resolve to the same Account/Owner. Purchasing, Plan changes and Operator administration are web-only; general Account functions and DPA conclusion/download retain both-client access. A private implementation boundary does not create another FA-GLE-02 exception.

The no-pre-1.0 structural dependency rule has only two accepted exceptions: [ADR-0017](adr/0017-accessible-pdf-reports.md)'s exact PDFKit report-adapter graph and [ADR-0020](adr/0020-website-documentation-help.md)'s reviewed static-site/local-search graph. Neither is a general dependency waiver. Qualification failures return for the named fallback or a new client decision; they do not authorize another runtime/vendor by implication.

## Check, identity and Quota lifecycle

1. A Guest or confirmed Account supplies text, a web selection, PDF/DOCX or BibTeX/RIS. Multipart bytes enter only the verification program. Oversized reads abort; the raw file is deleted transactionally after recognized References are stored. Non-AI bibliography detection runs in every Plan, with correctable regions and separate rejected-entry presentation.
2. The owned deterministic parser structures free inputs; eligible paid AI extraction uses only text and grounded spans/fields. Ungrounded AI additions are marked but excluded from search/scoring until explicitly adopted. Chunk failure has one retry then a visible, local parser fallback. Structuring consumes no Quota.
3. Show recognized count and expected consumption before automatic search. When Quota is insufficient, offer the first N slots in input order or upgrade first. Reservations are atomic against immutable Owner/grant journal entries; they do not make a balance negative.
4. Per-Reference jobs search sequentially across responsible sources and concurrently across References, under global source budgets and fairness. Mandatory covered DOI handling precedes other identifiers/routes. Each source evaluates at most five Candidates: identifier Candidates first, then the fixed bibliographic sequence ([ADR-0024](adr/0024-identifier-candidate-budget.md)). Score before advancing; no extra source is queried after an unambiguous match. Deadlines and rate waits can produce incomplete evidence, never invented negative evidence.
5. Versioned deterministic scoring produces the exact six Verdicts, or separate technical Statuses. A high similarity alone does not prove identity. Source failures, coverage, ambiguous identity, DOI conflict and mixed evidence use the precedence in [ADR-0008](adr/0008-scoring-verdict-rules.md); abbreviated journals use [ADR-0018](adr/0018-journal-title-abbreviations.md). Similarity, field rules and fixed-point arithmetic follow [ADR-0025](adr/0025-comparison-profile.md); only its declared free parameters are calibrated, and an uncalibrated configuration is never releasable.
6. Results are append-only and bound to a field revision/configuration. Changing the preferred citation style re-renders Correction suggestions without touching Verdicts or stored results. Same-slot correction/Re-check is free while retained; new slots or restarting History are new billable work. A Manual override belongs to one result and resets visibly on Re-check. Export-only corrections do not edit stored evidence.
7. Explicit cancel/reset or lease expiry preserves finished Verdicts, releases unfinished reservations and rejects late results. A disconnected panel alone is not immediate cancellation, and this is not deferred background execution. Reconnect uses current authority, snapshot and ordered event replay.

These mechanisms and their detailed edge cases are authoritative in [ADR-0004](adr/0004-owner-plan-quota.md), [ADR-0005](adr/0005-check-reference-lifecycle.md), [ADR-0007](adr/0007-search-strategy-latency.md), [ADR-0010](adr/0010-ai-provider-model.md), [ADR-0011](adr/0011-non-ai-structuring.md) and [ADR-0016](adr/0016-results-presentation-workflow.md).

An **Account signs in; an Owner holds Quota, Plan and Checks**. A confirmed Account has exactly one personal Owner. Feature scope is the union of current grants, with earliest-expiry allocation and provider-business-object idempotency. A future organization adds an Owner and memberships without replacing the personal Owner or its History/Plan. Guest IDs remain separate per client environment; registration transfers neither Guest content nor grants. Future identity methods map issuer/subject to the stable Account with proof-of-both-accesses linking.

Hosted authority fails closed. The five-minute API JWT does not override revoked sessions, blocks, deletion or current named permissions. The service checks current authority for protected requests and continuing streams/downloads; workers recheck at dispatch/commit. The Guest removal code in ADR-0022 is a deletion-only capability through the current-authorized API entry, not a content-read token. Detailed email-code, session lifetime and transport/fresh-proof rules remain [ADR-0013](adr/0013-authentication-roles.md).

## Data lifetime and rights

| Record class | Accepted lifetime/handling | Boundary and qualification |
| --- | --- | --- |
| Check without History | Delete no later than 24 hours after Check end; fixed deadline, no Re-check extension; abandoned pre-start Check expires from creation | Verification-side content; no persistent browser content; backup crypto-shredding must be proved |
| Consented History | Free: last five usable Checks under 30 days; paid: initial 90 days; downgrade locks other entries without extending their dates | User deletion/revocation and tombstone replay; usable access and physical retention are distinct |
| Temporary PDF | At most 15 minutes and never beyond the Check deadline | Verification-side generation snapshot and current-authority download; no sharing link/archive |
| Reported wrong Verdict | Separate proposed 90-day maximum from receipt, subject to legal qualification; withdraw/deliberate Check/Account/Owner deletion earlier | Should hook only; consent/notes/removal credential expire with copy; Guest/Owner association; no dataset copy |
| Limiter/security/audit | Counters ≤24 hours; content-free security events 30 days; administrative audit initially 12 months | Separate purposes and minimized identifiers; not a content/consent archive |
| Billing | Baseline eight-year restricted invoice evidence, separately archived | OSS ten-year candidate C03 is not adopted; no blanket extension to other records |
| DPA/support/rights | Legally qualified, purpose-specific schedule; no automatic eight-year DPA archive | Exact packet/conclusion evidence separate from verification data; return/access requests do not extend content expiry |
| Backups | Existing bounded backup tail up to 14 days for applicable retained data; transient keys excluded/shredded; replay deletions/expiry/blocks before traffic | Restore cannot resurrect readable erased content or pre-restore sessions; actual provider/export/key behavior needs Q06/Q09 |

Consent for History, reporting, marketing, immediate paid activation and DPA acceptance are distinct records and purposes. Statutory data-subject export, contractual return, exact DPA download and ordinary citation export have different scopes/authority. Deliver only actually retained data to a verified entitled recipient, including purpose-limited blocked/deleted-account cases where applicable; no invoice/profile-only takeover, account resurrection, ordinary Operator preview or backup recovery. Short-lifetime fulfilment must actually be feasible. See ADR-0014/0021/0022 and Q09.

## Commercial, information and operating surfaces

Stripe is the selected direct-merchant processor; Source Taster owns Orders, catalog versions, consent, public statutory cancellation and invoice/tax evidence. The own order page binds terms/gross price/obligation-to-pay before hosted payment collection. Grants follow confirmed paid business objects, never redirect/webhook delivery alone. Delayed activation, failed renewal, refunds and provider outage reconciliation follow [ADR-0009](adr/0009-payment-provider-tax-model.md). Stripe plus a named contracted EN 16931 integration must prove invoice/PO/non-Peppol capability; Mollie is only the qualified fallback. Actual one-time/recurring PayPal, legal seller and tax/consumer flows are not established by this record.

Routine Operator work uses the small private web UI at launch, with fresh-proof critical actions, server-side validation, recoverable operation IDs and controlled audit reasons. It manages Accounts, catalog/limits, credits/blocks/temporary Pro, measured-configuration activation, accounting exports, recipient-only rights fulfilment and review tasks. Payment/hosting provider administration remains appropriate for its own tasks. There is no generic database editor or terminal-only daily workflow.

The selected public information route is a bilingual static Astro site, local Pagefind search and one-click in-product help on the existing verification host, with the qualified Docusaurus fallback in ADR-0020. Public pages/indexes contain no customer/private material; there is no launch product analytics or external embed tracking. Every product/mail/invoice/site text is DE/EN. [ADR-0019](adr/0019-transactional-email-catalog.md) has **seven launch mail types**: sign-in, Order confirmation, purchase/invoice, failed payment, cancellation receipt, DPA receipt and intended subprocessor-change notice. The withdrawal receipt is reserved, not active; deferred messages and marketing are not silently enabled.

Scalingo Paris plus Scaleway storage/TEM/Cockpit is the selected operating route. Start-small cost estimates are conditional on real capacity and OS isolation; they are not a qualified €50–80 sandbox topology. Own availability is ≥99.5% monthly including planned downtime, with ≥48-hour maintenance notice. Independent six-hour exports, platform/fallback restores, a named deputy and the ≤24-hour RPO/≤8-hour RTO envelope are launch gates. The €650 infrastructure ceiling and upgrade triggers remain ADR-0012; AI/payment/support costs are separate.
