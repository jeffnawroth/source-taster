# Issue #84 — confirm or override a Verdict manually

Implements FA-ABG-16 under ADR-0005 (Manual override section), ADR-0016
(effective Verdict with manual indication) and ADR-0008 (overrides never change
Correction suggestions). The confirmed #70 seams are HTTP/SSE against real
disposable PostgreSQL with fixture Data sources, plus Playwright for the web app
and the real native Chromium side panel. No scoring, search, billing, Quota,
provider activation or qualification gate changed.

## Delivered behavior

- `POST /v2/checks/{checkId}/references/{slot}/manual-override` takes
  `expectedRevision`, `resultId`, `expectedOverrideId` (`null` for the first
  judgment) and one of the six Verdicts. It succeeds only for the current,
  finished, non-removed slot whose newest result has a Verdict and belongs to the
  current field revision and generation. A stale revision, an older or newer
  result ID, a stale override ID, a running slot or unverified saved fields
  return 409. Missing/removed slots and foreign Owners return 404, missing
  `check:create` authority returns 403 and the fixed content deadline returns
  410, matching the #83 mutation guards.
- The override is a separate `manual_overrides` row keyed by result ID
  (migration `20261030020000_manual_overrides`). Immutable result content,
  Candidates, Scores, identity, evidence, field revisions and Correction
  suggestion eligibility never change. Confirming the same Verdict is stored as
  manual too.
- v2 snapshots and Reference events expose `manualOverride` on the slot (only
  for the current finished result) and on every historical result.
  `manualOverrideReset` is true only when the result that the current run
  replaced carried an override. The notice therefore appears for the Re-check
  that reset it, while it runs and after it finishes, and disappears after a
  later Re-check or a new judgment. The old override stays readable on its
  historical result.
- Shared web/extension UI (`packages/ui`): a Manual judgment section with
  **Confirm Verdict** and **Judge manually** (draft select, Save/Discard).
  List rows and detail show "Manual Verdict: …" together with
  "Original system Verdict: …". Summary counts and filters use the effective
  Verdict and show "Manual: n" per Verdict. A Re-check shows the reset notice. A
  conflicting save reloads the snapshot and keeps the user informed instead of
  applying the draft to a different result. All text is DE/EN.
- Historical result sections and their comparison/failed-source landmarks carry
  a run label when more than one earlier result exists, keeping accessible names
  unique.

Documented edge: **Save fields only** (no run) makes the current outcome *not
checked*. The override then no longer applies to the current slot, but no reset
notice is shown because no Re-check happened. It stays on its historical result.
A later Re-check shows the notice.

## Integration handoff

- Consumers that count or filter Verdicts must use the effective Verdict
  (`manualOverride?.verdict ?? outcome.verdict`, Status first). See
  `packages/ui/src/effective-verdict.ts`. Exports and bibliography rendering keep
  using system evidence only.
- The Verification report (#78 story, later ticket) and reported-wrong-Verdict
  copies (ADR-0022) should read `results[].manualOverride` to include manual
  changes with the system Verdict retained.
- `schema.prisma` gains `ManualOverride` and a back-relation on
  `ReferenceResult`. Parallel tickets adding migrations or editing
  `ReferenceResult` may conflict textually there. Regenerate the Prisma client
  and contract artifacts after resolving.
- Generated `packages/contract-verification/dist/**` and `openapi-v2.json` were
  regenerated by the package build and are reproducible from source.
