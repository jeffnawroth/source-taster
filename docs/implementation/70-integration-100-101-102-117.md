## Interaction findings and rulings

1. **Deletion removes Account Preferences, no copy to Guest.** In the merged
   code, deletion ran the #101 session-end path, which copies the last
   displayed values into Guest storage. ADR-0023 says Preferences "are deleted
   with" the Account ("Account deletion removes the Preferences"). Only sign-out
   and session expiry copy. #102 requires that deletion clears Account storage
   and that in-progress deletion never falls back to Guest. Red:
   `merge-102-extension-account-red.log`: both extension deletion specs fail
   on an extra `source-taster-guest-preferences-v1` entry. Fix: the hook now has
   `forget()`, which fences pending Preference work and skips the copy. The
   shared `AccountWorkspace` (web and extension) calls it on every deletion
   outcome. Sign-out and expiry are unchanged and still covered by the #101
   lifecycle spec. Displayed values stay in memory only.
2. **#99's mount-time Guest Quota read after deletion. USER DECISION: no
   read on mount; the Quota is read at the first Start.** `aee07b4` read the
   Quota when a hosted workspace mounts. After a *completed* deletion the
   workspace remounts as Guest, so it requested a Guest token and read the
   Guest Quota at once. On the web a fresh context can mint a new device Guest
   identity that way. The user ruled that this must not happen. Now:
   - After a completed deletion the hosted workspace (web and extension) does
     not request a Guest token and does not read the Quota on mount.
     `AccountWorkspace` passes `deferQuotaRead={removal === "deleted"}` to
     `CheckWorkspace`, which then skips its mount-time read.
   - The Quota slot is neutral: nothing is rendered, the same as where no Quota
     applies. No "loading" or "unavailable" text, because nothing is loading or
     failing. No new copy, so no DE/EN change.
   - The first Start uses the existing fail-closed start read (`readQuota()`
     before `planStart`). It requests a Guest token, reads the Quota, and the
     meter then shows. A failed read still stops the Start. The ordering is
     unchanged: structuring first, then the Quota read, then Check creation.
   - The extension keeps its existing Guest ID. Storage is exactly
     `{source-taster-guest-id-v1: <same id>}` after deletion and after the Start.
   - A plain Guest visit that is not after a deletion is unchanged (#99: Quota
     visible before the first Start). In-progress deletion still makes no Guest
     request (unchanged #102 assertions).
   - Limit: the deferral lives in the workspace state, not in storage. Storing a
     "deleted" marker would keep a trace of the Account that ADR-0023 and #102
     say must not remain. So a page reload after a deletion is a plain Guest
     visit and reads the Quota on mount like any other. A spec asserts that.
   - Also asserted: no Guest token or Quota request before the deletion answer,
     no Preferences/Account-token/activity request after deletion, and no
     Account ID, Owner ID or email left in storage. No content or grant moves to
     Guest, and no Account-to-Guest restoration exists.

   Evidence (test-first; logs in `.tmp/spec-70-orchestration/merge-103-*`):
   - Web `e2e-sensitive/sensitive.spec.ts`, "after a completed deletion the
     Guest workspace requests no Guest token and no Quota until the first
     Start". Red (`merge-103-web-sensitive-red.log`): after deletion the page
     had requested `["guest-token","quota","quota"]` (the second `quota` is the
     dev build's double effect); expected `[]`. Green: `[]` until Start, no
     Quota meter, then `["guest-token","structuring","quota"]` after Start and
     the meter shows.
   - Web control, "a plain reload after a deletion is a plain Guest visit":
     passes before and after; the reload reads token and Quota on mount.
   - Extension `e2e-account/sensitive-panel.spec.ts`, "after a completed
     deletion the panel requests no Guest token and no Quota until the first
     Start, which keeps the existing Guest ID". Red
     (`merge-103-extension-sensitive-red.log`): a `guest-tokens` request after
     the deletion answer. Green: no service or API request until Start, then
     a Guest token POST and `GET /v2/quota` with that token, Guest ID unchanged.
   - Harness: Guest traffic is answered by in-browser routes (web) and a
     recording stand-in API (extension), via
     `apps/server/test/support/guest-start-stub.ts`, because the stand-in
     service has no Guest identity. These fixtures prove when requests happen,
     not Guest identity or a real balance. The extension specs now take their
     ports from `SOURCE_TASTER_ACCOUNT_TEST_SERVICE_PORT` and
     `SOURCE_TASTER_ACCOUNT_TEST_API_PORT` (defaults 4902/4901).
   - Re-run for the merge commit (red with the two `packages/ui` product files
     reverted, `merge-103-web-sensitive-red2.log` and
     `merge-103-extension-sensitive-red2.log`; green with them,
     `merge-103-web-sensitive-green2.log` 16/16 and
     `merge-103-native-account.log` 26/26).
   - Plain-Guest-before-first-Start is unchanged: the #99 spec "the Guest sees
     count and consumption before the start and the balance afterwards" and
     "a returning Guest sees the real, already reduced balance before starting
     again" pass (`merge-103-web-quota.log`, 8 of 9), and so do the "refused
     Guest" and "pending session" cases. The default web e2e passes 87/87
     (`merge-103-web-default2.log`).
   - Known failures that also occur **without** this change (reverted product
     files, `merge-103-web-quota-baseline.log` and
     `merge-103-web-guest-baseline.log`): the quota spec "a signed-in Account
     sees its Free Quota before starting" (the Account email never appears; a
     signed-in view, not touched by the deferral), and the timing-sensitive
     Guest-lease spec "revocation stops renewal" (`renewals` changes during the
     1.5 s wait; passes in some runs, fails in others, with and without the
     change). In one of four Guest runs with the change, "Guest identity survives
     a real browser restart" also failed once (Quota still loading, 5 s wait);
     it passed in the other three and in the baseline run. Not investigated
     further here.
3. **#101 lifecycle × #99:** after sign-out the extension may now hold its own
   Guest ID beside the Guest Preferences. The spec asserts the Preferences
   entry exactly and that it is not keyed to that ID (ADR-0023).
4. The #102 private-service stand-in got an in-memory `/preferences`
   GET/PATCH. Without it, 9/14 web sensitive specs failed on the extra
   Preferences alert (`merge-102-web-sensitive-red.log`). This changes the
   fixture only.

No ADR conflict requiring a user decision was found.
