# Non-AI structuring and citation tools

Research date: 2026-10-24. Resolves [wayfinder research #8](https://github.com/jeffnawroth/source-taster/issues/8), under [map #4](https://github.com/jeffnawroth/source-taster/issues/4). Research recommendation only; no runtime exception, dependency selection, requirements change or legal approval is made here.

## Scope and evidence status

The application is TypeScript end-to-end, with no pre-1.0 structural core. This investigation separates extraction, bibliography delimitation, reference splitting, semantic field parsing, structured interchange and rendering. Capability in one layer is not evidence of another. The English requirements v3.1 remain unchanged; all eleven styles may be included in the Reference test set because section 14.4 specifies a minimum of five, not a maximum.

Evidence is drawn from official repositories, documentation and package metadata retrieved on the research date. “Verified” below means documentary/source verification, not product acceptance. No user documents were uploaded, production services provisioned, paid APIs used, or quality/throughput tests run. Empirical acceptance remains outstanding.

## Research conclusion

There is a conditional JS/TS component shortlist for extraction, formal interchange and rendering. The principal feasibility gap is the owned rule-based bibliography detection, splitting and semantic parsing path; no examined package proves the unchanged acceptance gates under the fixed constraints.

## Extraction and non-AI parsing feasibility

### PDF and DOCX extraction

**Verified:** PDF.js `PDFPageProxy.getTextContent()` returns text items with strings, direction, transform/geometry, width/height, font name and `hasEOL`; `streamTextContent()` is also available. Marked-content inclusion and normalization are options. These are page-content APIs, not a guaranteed logical reading-order or bibliography API. [PDF]

**Inference/design candidate:** retain page/item coordinates and source spans, reconstruct lines/columns, remove repeated running headers/footers conservatively, and distinguish genuine line-break hyphenation from DOI/URL/title characters. A two-column page can interleave references if strings are merely concatenated. Missing font/ToUnicode mappings can corrupt text even in born-digital PDFs. Tagged PDF structure may help when present, but is not a universal guarantee. Preserve extraction warnings and let users inspect the extracted bibliography and change its boundary; never claim “PDF text extracted” means references or CSL fields recovered.

**Verified:** Mammoth `extractRawText()` ignores formatting and emits two newlines after each paragraph. Its HTML conversion retains selected semantic structure, with support documented for tables, notes and text boxes; text boxes are emitted as separate paragraphs after their containing paragraph. It does not reproduce page layout or sanitize output, and external file access is disabled by default. Its document-transform API is explicitly unstable despite the stable package major version. [DOCX]

**Inference/design candidate:** compare raw-text completeness with a sanitized semantic representation for headings and paragraphs. Do not hinge the structural core on Mammoth's unstable transform API without a deliberate solution. DOCX ZIP/XML parsing of selected OOXML parts using stable JS ZIP/XML libraries is a more explicit alternative when style/list metadata is essential, but is custom work with a larger completeness/security burden. Embedded reference-manager fields can provide a separate structured import optimization (BiblioJSON); their presence in some DOCX files does not prove capture of an ordinary pasted bibliography. [BIBLIO]

A PDF with no extracted text needs the required explanation and content-free counter, not a silent OCR attempt or upload to a public converter. Image-only pages in a mixed PDF are a distinct completeness risk: non-empty document text does not show every bibliography reference was recovered. Decide how to report encrypted, malformed or partially extractable files without counting all of them as scanned PDFs. No OCR runtime or paid extraction endpoint is shortlisted for launch here.

### Bibliography boundaries and splitting

**Research gap:** PDF.js, Mammoth, BiblioJSON, Citation.js and CSL processors do not document a general automatic bibliography detector satisfying FA-ERF-05. Under the fixed rules, the practical conforming candidate is application-owned deterministic TypeScript logic, using headings such as References/Bibliography/Literaturverzeichnis, section hierarchy, page position, numbering and indentation, author-year starts and continuation-line geometry. It must handle missing headings, appendices after the bibliography, wrapped references, page breaks, multiple columns, running headers and unnumbered lists. Candidate boundary scoring is an algorithm idea, not evidence of 95% document success.

Boundary detection selects a region; splitting turns that region into references; semantic parsing assigns fields inside each reference. Keep diagnostics and source spans across all three so users can move start/end, restore a missed reference or repair an accidental merge/split. A “one reference per line” raw parser contract does not excuse document splitting: FA-ERF-05 supplies those references. Manual repair is no substitute for automatic acceptance.

### Raw-reference semantic parsing

No established JS/TS package examined provides documented broad rule-based field parsing across the relevant English/German reference forms with evidence for the parser-path verdict targets. BibTeX parsers handle a formal tagged/braced language; RIS parsers handle tagged records. Neither parses an APA bibliography line merely because it can export APA afterwards. Identifier regular expressions can recognize DOI/ISBN/PMID/arXiv values but do not recover an arbitrary author/title/journal partition.

Chevrotain and Peggy are maintained stable parser-building tools, not bibliographic grammars. A conforming TypeScript design could combine deterministic identifier/date/name patterns, style-aware grammars and conservative unknown fields, preserving original text and allowing edits. This requires product-owned design, corpus work and empirical iteration; it is **not** an off-the-shelf solved feature. Do not fill uncertain fields from a lookup before recording what the original reference actually said, because comparisons would otherwise hide deviations.

### Established external-runtime comparisons, not adopted solutions

- **refextract** is the strongest rule-based comparison: its official `find.py` and `engine.py` use heading/marker/regex logic and knowledge bases, with PDF conversion via `pdftotext`. Its own output has raw references and bibliographic dictionaries, not automatically CSL-JSON. The physics-heavy journal/report examples and knowledge bases do not establish German books, web sources, APA correctness or the 19/20 target. It requires Python plus a native PDF tool, so a TS HTTP wrapper would still be an **unapproved runtime exception**. Porting rules would be substantial TS work and inherit applicable code/data obligations; no port is proposed as already authorized. [REFEXTRACT]
- **AnyStyle** has separate Finder and Parser models, can be trained, and uses CRF/Wapiti. The README's sample language counts strongly favor English (measured on an older dataset); its warning about training-language representation matters for German references, but is not a current accuracy measurement. Finder training sources are explicitly not available in full because of copyright restrictions. It uses Ruby and native model inference and is **learned ML, not the specified rule-based free parser**, even when self-hosted and free of per-call fees. Both runtime and method would need client approval. [ANYSTYLE]
- **GROBID** has document segmentation, bibliography/reference segmentation, names and citation models. It consumes layout tokens from pdfalto, not a plain PDF.js text string. The README's claimed approximately .87/.90 reference extraction F1 and .90 instance/.95 field reference parsing F1 concern particular scholarly datasets and deep-learning configurations; they are not FA-ERF-05 document-level success or Source Taster verdict targets. The default uses CRF models; a CRF is still learned ML. Java/native components, optional Python/JEP/GPU and the pre-1.0 core independently violate current constraints. Public demos are not an approved processing endpoint. [GROBID]
- **CERMINE** bundles Java tools and learned models, outputs NLM JATS and parses isolated references. Its established 1.13 major version avoids only the numerical pre-1.0 problem; it does not avoid the runtime/method exceptions or old-maintenance risk. No separate blanket approval of model/data rights follows from the AGPL code license. [CERMINE]

A managed external parser would add third-party document processing, contractual/privacy review and operating dependence without making its implementation TypeScript or its learned model rule-based. It is not a shortcut within the fixed constraints.

## Structured interchange, CSL data and correction rendering

### Import/export fidelity: evidence and concrete limits

**Citation.js (comparison, excluded core):** official plugin documentation and inspected 0.9.0 tarballs support BibTeX/BibLaTeX text/objects ↔ CSL-JSON and RIS input/output, with configurable type mappings. It is an interchange toolkit, not an arbitrary reference-string parser. RIS source accumulates repeatable tags, joins continuation lines with a space, maps names and dates, and truncates exported IDs to 20 characters. Its RIS date conversion writes one date-parts tuple, not an arbitrary date range; name conversion cannot represent every name component. These are reasons to preserve originals and test fidelity even if the pre-1.0 rule changed. Avoid the umbrella package's DOI/Wikidata fetch plugins for a local file import; a text import should not silently resolve or enrich supplied references. [CITATION]

**BiblioJSON 4.1.0 (conditional import shortlist):** the tarball ships native TS parsers, CSL import/export, diagnostics and options for raw text/source offsets and unknown/unexpected fields. It models rich text, names and EDTF dates in its own intermediate representation precisely because CSL cannot represent every BibLaTeX detail. The README's absolute-sounding losslessness goal is not demonstrated acceptance, and its older FAQ says unspecified fields are dropped unless the relevant options are enabled. Preserve the raw record and diagnostics regardless. Its DOCX/ODT manager metadata reader is useful only when metadata actually exists. [BIBLIO]

Concrete source-inspected limitations, **not executed test results**:

- `src/import/ris.ts` accepts continuation lines beginning with six spaces and joins them with newlines. Dialects with other continuation conventions need evidence. Names containing commas use only the first two components, so a third suffix component is not retained by this method; multiword corporate names without commas are treated as personal names by the last-word heuristic.
- Its RIS conversion chooses PY/Y1 when present before considering DA/Y2. A record with `PY - 2024` and a more precise `DA - 2024/05/19` therefore risks losing month/day; access date and publication date must also remain distinct. This needs a targeted test and correction before relying on it for complete import.
- The actual exported API exposes `BibLatexExporter` and `CSLExporter`, not an RIS exporter or a dedicated traditional BibTeX serializer. `BibLatexExporter` emits BibLaTeX field/type mappings (for example `date` rather than merely `year`). Zotero may read that, but FA-ERG-30 explicitly says BibTeX: either prove the agreed export contract or provide a traditional BibTeX adapter. Do not count the package-description word “BibTeX” as proof of that export.
- The README expressly qualifies EndNote/Citavi/Mendeley conversion testing because proprietary programs are harder for maintainers to access. Vendor compatibility is not established by a package feature list.

**Citestyle BibTeX 1.1.0 / RIS 1.0.1 (small JS alternative):** documented BibTeX features include LaTeX-to-Unicode mappings, `@string`, concatenation, braces, particles, suffixes and corporate names, with direct CSL-JSON serialization. The packages ship conditional-export type declarations. However, inspected source narrows the RIS README claims: `parseRis` skips every line without a tag match, so continuation text is dropped; it maps `SN` to ISSN even for books, discards the original tag map on finalization, and uses a timestamp-based fallback ID. It chooses PY/Y1 before DA, similarly risking date precision. There is no translator mapping in the inspected parser despite the README's contributor-role claim. `exportRis` reduces dates to the first tuple and cannot preserve all CSL date forms. Its BibTeX exporter emits year/month without the day and maps every thesis to `phdthesis`. These are real source behaviors, not hypothetical lossless round trips. Client acceptance would require fixes/adapters and fixtures. [CITESTYLE]

**Retorquere parser 12.1.13:** used by Better BibTeX imports, default TS parser plus `parseVerbatim`, normalized fields, multiple preambles and diagnostics for unknown TeX commands. It is not a direct CSL-JSON mapper or exporter, and its README says bundled unabbreviations are on by default. Journal expansion and sentence-case processing must not silently change what was supplied for comparison. Default TS use needs no Rust toolchain or separate service; the optional WASM entry point and building it from source are separate choices. The dependency graph includes an English NLP model for text transformations, so this is not automatically a purely rule-based path just because its BibTeX syntax parser is formal. Prefer retaining the verbatim representation and explicitly disabling nonessential enrichment/learned transformations if this candidate is examined further. [RETORQUERE]

Zotero’s own [RIS translator source](https://github.com/zotero/translators/blob/8fdb26b68c732b5810ffb037304c99e68aadd62b/RIS.js) has explicit `EndNoteCleaner` and `CitaviCleaner` logic, Citavi H1/H2 tags, and EndNote-specific access-date/type mappings. This primary vendor code confirms that “RIS supported” does not imply interchangeable dialects. It also includes translator test fixtures; those are upstream evidence, not tests executed for Source Taster. The [BibTeX translator](https://github.com/zotero/translators/blob/8fdb26b68c732b5810ffb037304c99e68aadd62b/BibTeX.js) is a useful interoperability oracle with its own rights; copying it would require a separate license audit.

For **every** candidate, CSL-JSON mapping needs an explicit loss policy. Personal names (family/given, particles, suffixes), literal corporate authors, multiple authors/editors, partial/ranged/literal dates, access dates, multilingual titles, LaTeX accents, Unicode normalization, rich-text case protection, DOI/URL/ISBN/ISSN/PMID and book/chapter/container distinctions must be checked individually. Unicode in a JS string is not proof of correct import encoding or name interpretation. Neither record count nor successful JSON validation proves those fields survived.

A reasonable data design for FA-STR-01 preserves the unmodified original reference or structured record, canonical CSL-JSON, field/source provenance and import warnings; retain the raw tagged/braced record separately from its normalized CSL projection. BiblioJSON can be an internal loss-preservation sidecar without replacing the required CSL data. The official CSL-JSON schema supports names, date objects and bibliographic types, but its maintainers warn the schema is not yet fully normative: validate both schema and actual processor/Zotero behavior. [CSL]

Keep the imported CSL data separate from the correction suggestion built from the best match's source data. Applying a correction for export should be explicit (FA-ERG-14/30), leaving original input retrievable; for structured imports, original text is the record as supplied, not a newly fabricated APA citation. The requirements do not expressly demand byte-for-byte preservation of every unsupported vendor field; clarify “complete” before declaring an interchange acceptance pass. Preserve unsupported fields rather than silently dropping them in the meantime.

### Renderer and style evidence for all eleven families

citeproc-js accepts item/locale retrieval functions and style XML; `updateItems` and `makeBibliography` render bibliographies. It offers text/HTML output modes and citation APIs; it does not locate references or parse bibliography prose. A typed adapter can supply only locally bundled styles/locales and validated CSL items, keeping the operator's processing under their control. Pin processor, exact style file, locale and rendering options so corrections are reproducible. A per-reference suggestion may need bibliography context for numeric ordering/disambiguation; note styles need a deliberate choice between full note and bibliography entry. ## Conditional shortlist and reasonable alternatives

**Recommended next decision path under the actual constraints (opinion):** keep the pipeline in TypeScript/Node; investigate **direct PDF.js + Mammoth**, **BiblioJSON for formal imports with documented fixes/loss policy**, and **direct citeproc-js with pinned official CSL styles/locales**. Use a product-owned deterministic boundary/splitting/raw-parsing module with source spans and editable fields. This is a **partial component shortlist with an explicit custom-core feasibility gap**, not a claim that launch requirements are now solved. Source inspection supports the component roles; a license audit and empirical gates still control adoption.

Reasonable alternatives:

1. **Citestyle BibTeX/RIS + its renderer:** smaller direct-CSL packages and stable 1.x numbering, with type declarations and no extra service. Only viable after continuation-line, date, identifier, name/type mapping and processor-context issues are fixed/proven. Its current broad marketing claims do not override inspected omissions or upstream style rights. Traditional BibTeX export is more explicit than BiblioJSON's BibLaTeX exporter.
2. **Retorquere BibTeX parser + owned CSL/export adapter:** rich Bib(La)TeX syntax and verbatim access; no RIS coverage and more integration/data-provenance work. Use default TS entry, not optional WASM, if keeping the dependency purely JS at runtime matters. Audit/disable model-based transformations and enrichment separately from syntax parsing.
3. **Owned formal BibTeX/RIS import/export adapters around stable grammar tools:** avoids pre-1.0 conversion core and permits explicit provenance/fidelity policy, at significant engineering and maintenance cost. A standards subset cannot silently replace “complete” manager imports.
4. **AnyStyle/refextract/GROBID service comparison:** useful only if the client later chooses to reopen runtime/maturity/method constraints. refextract stays closest to rule-based parsing; AnyStyle/GROBID/CERMINE introduce learned methods. No external-runtime service is accepted by this research.
5. **Citation.js later stable release or explicit maturity exception:** broad interchange capability is relevant, but neither waiting for a speculative 1.0 nor silently adopting 0.9 satisfies today's fixed rule. A stable top-level wrapper around a pre-1.0 structural core does not remove that constraint.

**Unresolved feasibility/cost gaps:** automatic boundary/splitting success 19/20; raw semantic field parsing and downstream parser verdict quality; complete 20-document extraction evidence; stable formal-import mappings without data loss; selected eleven style definitions and DIN edition; AGPL-compatible packaging with third-party models/data/styles; bounded 20 MB/1,000-reference resource usage. Runtime/language/maturity constraints cannot be “solved” by putting an HTTP endpoint in front of the excluded engine. Research is complete when these gaps are documented; choosing an approach and passing their gates are later work.
